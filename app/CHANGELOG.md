## [1.33.0] - 2026-11-14

### 新版本检测与更新提醒

- 新增 `server/modules/update-checker/`：定时（默认 6 小时，1-168 可配）调用 GitHub Contents API 读取仓库 `app/VERSION`，与运行版本比对；发现更新时通过既有通知系统推送「新版本可用」事件，每个版本只提醒一次（`lastNotifiedVersion` 随状态持久化，重启不重复提醒）。

- 检测为纯只读（Contents:read），失败计入状态并吞异常，不影响录制/备份/上传主链路；更新本身仍由人工确认后在服务器执行发布脚本，不新增任何自动部署逻辑。
- 服务器同步提供 `scripts/update-from-repo.sh`（部署为 `/opt/shn48/scripts/update-from-repo.sh`）：确认后一键执行「Deploy Key 只读拉取仓库 → 本地构建候选镜像 → 切换 → 等待 healthy → 健康接口与运行文件哈希核验」，活动任务运行中自动拒绝切换，失败自动回滚 compose 与旧镜像，旧容器仅列出待人工确认清理。
- 通知事件列表新增「新版本可用」（默认开启）；7 项 update-checker 专项测试覆盖配置校验、版本比对、去重提醒、失败记录与状态持久化。

### 无人值守与内容工作台八项新功能

本轮按 2026-11-01 规划实施八项功能（外部通知推送、跨归档字幕搜索、AI 高光切片、弹幕高能时刻、口袋48关键词监控、公开总结日报/RSS、真实转码导出、AI 投稿标题简介），全部为兼容新增（新模块/新端点/新页面，不改变既有接口与数据格式），已随 1.32.0 以 MINOR 发布。

**第二轮自审修正（同轮追加）**

- **通知总开关真正管住所有外发**：连续失败告警此前在总开关关闭时仍会外发（告警分支在 enabled 判断之前），现在 `event()` 先检查总开关再决定任何投递，与设置页"关闭后不再外发"的文案一致。
- **已存密钥可清除**：掩码输入"留空=保持不变"意味着密钥一旦保存无法移除；通道配置新增 `clear:[字段…]`，设置页每个通道出现"清除已存密钥"按钮（仅当已存密钥时显示）。
- **邮件 TLS 端口自适应**：`secure` 不再固定 true——未显式配置时按端口推断（465 隐式 TLS，587/25 明文起连并按服务器通告 STARTTLS 升级），修复端口填 587 时必然 TLS 握手失败的问题。
- **归档完成通知每录像一次**：`done → processing → done` 的"重新整理 MP4"路径此前会再次推送"归档完成"；现在在录像上打 `archiveNotified` 一次性标记（随状态迁移原子落盘），归档失败时清除标记——之后成功作为"恢复"再通知一次，与"失败告警 + 恢复"对称。
- **关键词监控冷却跨重启持久化**：命中冷却时间戳此前只在内存，服务重启后最近一轮命中会被重复推送；现持久化到 `keyword_monitor_state.json`（2 秒防抖）。
- **公开日报/RSS 降载**：聚合改为直读 `analysis_<id>.json`，不再经 `service.result()` 每场重复从磁盘加载 analysis_jobs 队列。
- **搜索跳转 `?t=` 跨录像重置**：从搜索页连续打开不同归档时，seek 定位只消费一次的标记会随录像切换重新武装。
- **通知设置页补齐**：事件开关列表补上"转码导出完成/失败"（后端事件已存在但页面未渲染，等于不可配置）。

**1. 外部通知推送（`/admin/notify`）**

- 新增 `server/modules/notify/`：Telegram / 邮件（内置零依赖 SMTP 客户端，支持隐式 TLS 与 STARTTLS、AUTH PLAIN/LOGIN）/ Server酱 / Bark / 通用 Webhook 五个外发通道；密钥只落服务器数据目录，设置接口只回显 `xxxSet` 布尔。
- 事件挂钩：开始录制（`manager.insertRecording`，重连分段与剪辑行不通知）、归档完成 / 录制失败（`updateRecording` 状态迁移）、B站投稿完成 / 失败（`updateQueueItem`）、115备份完成 / 失败（backup115 收尾与终态）、分析任务完成 / 失败（分析 worker 队列）、转码导出完成 / 失败；逐事件开关可配，"分析任务完成"默认关（长转写逐场通知易吵）。
- 连续失败告警：录制 / 投稿 / 备份 / 分析 / 导出五个域独立计数，连续失败达阈值（默认 3 次）额外发一条告警，任一成功即清零；同一域告警有冷却窗（默认 60 分钟），半夜不再被轰炸。
- 发送失败自动重试一次（3 秒退避），投递记录（最近 200 条）落盘并在设置页展示；设置页含每通道"发送测试"（缺凭据时指名缺失字段）。
- 通知模块单向只读调用方数据、`event()` 全程吞异常：通知故障不可能影响录制 / 备份 / 分析主链路。

**2. 跨归档字幕全文搜索（`/admin/search`）**

- 新增 `analysis/search.js`：扫描数据目录 `analysis_<id>.json`（精确匹配，排除 `_before_*` 备份与总结断点），输入关键词返回命中场次、成员、时间点与原文，点击跳转 `/admin/archive/:id?t=<秒>` 自动定位播放（详情页支持 `?t=` 一次性 seek）。

### 字幕识别与回放链路迭代

依据 2026-10-31 字幕识别链路审计（14 项）与回放链路审计（13 项）实施，关键指控逐项亲核后修复。

**字幕识别**

- **离线识别分块修复（可用性主线）**：离线转写恢复按 `ASR_CHUNK_SECONDS`（默认 600 秒）分块。此前离线分支把整段录像当一块（86400 秒），叠加 worker 10 分钟硬超时与"整块完成才落盘"，2-3 小时的直播录像必然超时被杀、进度恒 0、重试从零开始，永远无法完成；现在每块独立抽取→转写→立即落盘，进度实时可见，录制抢占或失败后从已完成块续跑，与文档承诺一致。离线路径不再把整块音频读进内存构造从不发送的请求体。文档同步修正（分块进度语义、已失效的"2 秒终止"表述、CPU 线程数与实际一致）。
- 指纹变化（SRT 导入的记录无指纹、词库/模型/端点变更）触发重新识别且已有非空字幕时，先写 `analysis_<id>_before_retranscribe` 备份再重置——此前手动纠错与导入内容会被静默丢弃且无备份；前端对已有字幕的重新识别弹确认并说明还原点。

- 溯源"语音识别"阶段补写完成时间与启用词库，不再恒显"信息不全"；删除归档时级联清理 `analysis_<id>.json` 与全部 `_before_*`/总结断点（精确匹配防相近 ID 前缀误删），数据目录不再慢性膨胀；等待录制期间仅在阶段文案变化时落盘（不再每 3 秒全量 fsync）；手动纠错保留换行（编辑框与 SRT 本就支持多行）。
- 面板渲染瘦身：4 秒轮询深比较短路（空闲时零重渲染）、WebVTT 字幕轨按内容签名重建（播放中不再每 4 秒重载）、播放位置更新 500ms 节流、排队任务显示"前面还有 N 个任务"（已按服务端计数含本任务的语义取 N-1）；回放分析导入的状态轮询连续失败 5 次自动停止，不再无限双秒报错。

### 依据只读审计修复 15 项缺陷

**录制与存储**

- **重启前原片未进入归档**：异常重启后旧记录被标为 `failed`，同场新段仍挂该属主，但合并候选不收 `failed`，重启前可用的原片被漏掉。现在为重启中断单独打标记（兼容旧精确错误文案），仅在文件路径安全、非空、可解码、无录制写入、探测后大小/修改时间/inode/真实路径未变时恢复为待合并，且只调度重启型记录，任意其它失败记录不会被自动复活。
- **低水位清理绕过 24 小时原片窗口**：`sweep` 刚写入校验时间，同一轮的 `purge` 只检查时间是否存在就删原片。现在校验实际年龄，缺失、非法或未来时间一律保护；归档主文件仍永不自动删除。
- **失效回放下载计划永不刷新**：缓存计划里的分片地址失效后，重试仍用旧地址。现在遇到 401/403/404/410 且旧 worker 全部结束后最多刷新一次，重新校验同一个 liveId 与资源范围，同名但内容变化的资源不复用旧完成记录。

**分析与凭据**

- **更换服务端点沿用旧密钥**：设置页不回显密钥，管理员只改地址保存时会把旧 key 带到新主机。现在端点规范化后不同即清空旧密钥，请求前因缺密钥而拒绝；同一端点仍保留，显式替换与清除照常可用。
- **ASR 裁剪产生倒序区间**：片尾越界的字幕起点在容差内被接受、终点被夹到音频长度，输出结束早于开始。现在裁剪后重新校验正值区间。
- **混合无效候选整批崩溃**：任一候选带数组引用时，预检查无保护读取其它候选的引用导致 TypeError。现在缺引用的候选逐条丢弃，显式伪造/非法引用仍整批拒绝。
- **无依据高光被补造成“已验证”**：字符串高光与所有字幕都不匹配时被强行挂到第一条字幕并宣称覆盖完整。现在无匹配即丢弃，不再制造证据；证据策略升级后旧检查点不再复用。
- **内层重试吞掉 HTTP 状态与退避**：分片内部无条件重试三次，401/429 也立即重发，且不计入队列预算、遵循 `Retry-After`。现在移除内层循环，每分片每轮仅一次请求，HTTP 状态优先分类，401/403 不重试，429/5xx/网络交给队列既有自动重试、次数上限与退避。

**公开接口**

- **仅章节模式经分享预览泄露正文**：JSON 接口会隐藏总结正文，分享卡片却取原始结果写入 `og:description`。现在两者共用同一公开 DTO。
- **SSE 等待元信息期间断开泄漏**：访客在元信息返回前离开，仍会创建订阅与心跳。现在 await 之前就监听连接关闭，关闭后不再订阅、不建心跳，订阅同步回调断开也能回收。
- **直播上游故障伪装为空列表**：上游报错时返回成功的空列表，访客误以为无人直播。现在返回 502 且不泄露内部错误，真正的空列表仍为 200。

## [1.24.3] - 2026-10-21

### 修复自动签到失败后当天无法重试

排查线上「已暂停：口袋48请求失败（HTTP 200，业务码 401004）」时发现两个缺陷：

- **失败会占用当天**。`tick()` 在发出网络请求**之前**就把 `lastDate` 写成今天（这是为了防重启后重复签到，本身没错），但失败分支没有回滚。于是当天重新启用自动签到后，`lastDate === day(now)` 的守卫判定「今天已尝试过」，**直接跳过，当天再也不会真正签到** —— 界面一直停在「下次 10:29」，到点却什么都不发生。
- **旧报错与新状态互相矛盾**。`configure()` 重新启用时不清 `lastResult`，页面无条件渲染它，所以会出现「每天自动签到 ☑ 已勾选」与「已暂停：…」同时显示。这正是读者截图里看到的一幕。

修复：

- `tick()` 在进入时保存 `lastDate`，失败分支回滚为原值，当天重试即可真正执行。
- `configure()` 在重新启用且旧文案以「已暂停」开头时清空它。

### 关于 401004

`401004` 是口袋48 **业务层**返回码（HTTP 仍是 200，`success:false`），本项目只做透传、不做特殊解释 —— 它不是登录失效，也不是签到重复。实测定位：

- 同一账号在故障时段之外调用签到接口一切正常；今日已成功签到（`hasCheck:true`），重复签到返回 `400 今日已领取，明天再来`（正常业务提示，不是 401004）。
- `getCheckinInfo` 现在稳定返回 `200 success:true`。
- 因此 401004 属**口袋48 侧的临时性拒绝/限流**，重试即可，无需改配置。

### 测试

`server/test/auto-checkin.test.js` 新增「失败后当天重新启用应真正签到」用例，在**独立子进程**中运行以避开模块单例状态串扰。已做变异验证：临时移除 `lastDate` 回滚后该用例立刻失败（`实际 2026-09-20`），恢复后通过。

## [1.24.2] - 2026-10-21

### 修复口袋48「加载更早消息」看不见

读者反馈消息区底部只剩一圈虚线边框、看不见按钮。原因是**双重布局问题叠加**：

- 按钮原本排在**滚动内容的最后一项**。消息有 100 条时，正常阅读位置下它早已被滚出可视范围，只有边框从底边露出来。
- 更根本的是高度计算：`.p48-workspace` 只有 `max-height` 而没有确定高度，消息列因此按内容撑开（实测 120 条消息时高 **9783px**），而滚动区又写死了 `max-height: 720px` 并保留 `min-height: 320px`。结果是滚动区吃满 720px，把下面的元素顶出了设了 `overflow: hidden` 的工作区。

修复：

- 按钮移到滚动区**之外**，放进固定在消息列底部的 `.p48-stream-foot`，始终可见、不再随消息滚动。附带一条分隔线和底色，与消息区分开。
- 工作区改用确定高度 `height: clamp(620px, calc(100vh - 200px), 1400px)` 配 `grid-template-rows: minmax(0, 1fr)`，让 grid 行能够真正约束子项；`.p48-conversation` 补 `overflow: hidden`。
- 滚动区去掉写死的 `max-height` 与 `min-height: 320px`，改为 `flex: 1; min-height: 0` 由 flex 分配高度；两个窄屏断点里残留的 `max-height` 覆盖一并清除。

实测（120 条消息、三种视口）：按钮在 1440×1000、900×800、390×844 下都完整落在视口内，且滚动到列表顶部/底部时位置不变。

### 顺带修复窄屏面板重叠

单列布局下 `grid-template-rows: minmax(0, 1fr)` 会把成员列表和消息区压成同一高度导致**重叠**（成员列表文字压在房间标题上）。1150px 以下改用 `grid-template-rows: auto auto`、`height: auto`，并给消息列 `max-height: calc(100vh - 160px)` 作为自身约束。

### 测试

`client/test/pocket48-ui.test.js` 新增两条断言：`加载更早消息` **不再位于滚动区内**，且确实渲染在 `.p48-stream-foot` 底栏里 —— 防止以后又把它放回滚动内容末尾。

## [1.22.2] - 2026-10-20

### 修复：「仅成员」必然报"直播通知需要从房间列表中选择成员"

现象：点开成员后切到「仅成员」，消息区直接红字报错，任何成员都一样。

根因：**两个标识符被当成了同一个**。同一个房间在口袋48里有两套 ID：

| 用途 | 陈琳（实测，ownerId 6431） |
| --- | --- |
| 成员目录 channelId（QChat 频道号，成员列表传给前端的就是它） | 1279493 |
| 会话列表 targetId（聊天房间号，通知接口按它索引） | 67207851 |

「仅成员」作用域合并了 members + notifications 两个源。members 按 channelId 读频道没问题，但 notifications 走 chatroom/msg/list/homeowner，这个接口只认会话房间号。旧代码用同一个 id 去会话列表里找，永远找不到，于是直接抛 400。

实测确认：用会话房间号 67207851 调通知接口返回 200；用频道号 1279493 则被拒。

修复：ownerId 是两套 ID 之间的稳定桥梁。通知作用域先按 id 精确匹配（兼容老路径），匹配不到就用 ownerId 在会话列表里找回该成员的会话房间号再请求；连会话都没有时才退回原 id。新增回归测试：从成员列表的 channelId 进入「仅成员」时，通知接口必须被真实调用，且带上会话房间号与 ownerId。

## [1.22.0] - 2026-10-19

### 修复：重复归档互相引用导致谁都删不掉

现象：同一场直播的两条归档，删除任一条都报"文件仍被其他归档引用，暂不能删除"，形成死锁。

根因：`DELETE /recordings/:id` 把 `filePath`、`replayRecovery.replayFilePath`、`sourceFiles` 一视同仁地做交叉引用检查，任一文件被别的归档引用就整体拒绝。而同一场直播的两条归档天然共享文件——官方回放按 `liveId` 只存一份，重复归档的两条记录 `filePath` 甚至会指向同一个 `.official-replays/<liveId>/verified.mp4`——于是两条互相挡住，哪条都删不了。

修复：归档记录与物理文件解耦。删除记录时，只有当**没有其他存活归档引用**某个文件时才 unlink 它；仍被引用的文件从本条解除引用、留在盘上给它的持有者，既不会变成孤儿，也不会在别人的脚下消失。

响应新增 `sharedFilesKept` 字段并持久化到记录上，前端提示"另有 N 个与其他归档共享的文件被保留"，便于事后排查。

新增测试 `server/test/shared-file-delete.test.js`（3 项）：共享回放文件不阻止删除重复归档、两条共享同一主文件时可逐条删除且最后一条回收文件、被他人持有的片段只解除引用不 unlink。`archive-storage` 测试同步更新：原先断言"共享主文件 → 409"的旧规则已被这条修正取代。

### 修复："重新投稿"按钮点了必然报错

现象：录像归档列表里，点"重新投稿"报"仅允许对已修复的历史投稿录像重新投稿"，这个按钮对绝大多数录像都是死路。

根因是前端显示条件与后端门槛用了**两个不同的字段**：

- 前端 `Video.jsx` 的 `canRepost` 判断 `replayRecovery.status === "replaced"`（官方回放已替换）。
- 后端 `routes/recordings.js` 的 `POST /:id/reupload` 要求 `replayAudit.status === "repaired_local_published"`（历史投稿经审计修复）。

`replayRecovery` 是正常录制流程拿到官方回放就会写的字段；`replayAudit` 只有运行历史投稿审计修复时才会写。只看前者，任何"投过稿 + 被官方回放替换"的录像都会出现这个按钮，而后端一律 409——按钮出现即必然失败。

修复：`canRepost` 改为同时要求 `replayAudit.status === "repaired_local_published"`，与后端判据一致。"重新投稿"的语义是"本地存档在投稿后被修复，因此另建一份新草稿、原投稿不动"，只适用于审计修复过的录像；未修复的录像不应出现它。

注意这**不会**让你给普通已投稿录像重投。若确需该能力，得放宽后端门槛（去掉 `replayAudit` 限制，保留 B 站草稿冲突检查），属于另一次功能变更。

### 性能：公开落地页首屏 −71%

不含新功能。公开落地页首屏体积从 1036.2 KB 降至 303.5 KB（−71%）。原因是 `components/VideoPlayer.jsx` 在模块顶层静态引入 `hls.js`（579.2 KB）与 `flv.js`（152.5 KB），而该组件被 5 个页面静态引用，导致只显示直播列表的落地页也下载全部播放器代码；现改为按需动态引入，仅在真正开始播放时加载。

改动中有一个必须记住的约束：`import("flv.js")` 的结果**不能再取 `.default`**。`flv.js` 是 CommonJS 包，vite 在构建期自动注入 `.then(e => e.f)` 完成解包并直接返回库对象，再取 `.default` 会得到 `undefined`，FLV 播放报错但**页面与接口均无任何提示**（静默失败）。

### 修复：同一场直播被存档成两份

现象：录像归档列表里，同一位成员、同一场直播出现两条已归档记录（`2026-10-17-SNH48-杨晔-快乐🎵`，10:21 与 17:19 各一条）。

根因是「场次」和「录制进程」被混为一谈：

- `pocket48/recorder.js` 的 `start()` 只按内存表 `active` 去重，而 `active` 只包含**仍在跑的 ffmpeg 子进程**。子进程一退出（`finalize()` 里 `active.delete`）判定就失效，同一 `liveId` 的下一次启动直接 `addRecording` 建新记录。
- `manager.addRecording()` **没有任何按 `liveId` 的去重**。手动导入官方回放有 `existingArchive()` 挡重复，直播录制却没有，这条路径完全没设防。
- 归档处理器 `archive-processor.js` 只把「显式 `reconnectOf` 链 + 双方都有 `autoMonitorId`」的分段视为同场。服务重启（`manager.loadState` 把 `recording` 标成 `failed`，`state.lives` 的分段链丢失）、重连次数耗尽、手动录与自动录混用、间隔超过 15 分钟窗口，任一情况都会让分段打不上同场标记，退化成两条独立归档。

修复分三层：

1. **`manager.addRecording()` 增加场次级幂等**：同一 `source` + `liveId` 已存在非终态（非 `deleted`/`merged`）记录时，新启动不再另建归档，而是作为该场次的**分段**写入（`segment: true`、`sessionId: 指向场次属主`）。这是唯一能同时封住重启、重连、并发、手动+自动混用等所有路径的做法。
2. **`pocket48/recorder.js` 消除并发窗口**：新增 `starting` 占位表，在 `await liveService.getLive()` **之前**就登记该 `liveId` 的启动声明，第二个并发调用复用同一个 Promise，不再两个请求都通过 `active` 检查。
3. **`archive-processor.js` 认场次归属**：`sessionOf()` / `sameSession()` 把「属主自身 id」与「分段的 sessionId」解析到同一个场次；`compatible()` 对同场次直接判为可合并；`splitSessions()` 里会话链接优先于时间窗口，避免重启后 5/15 分钟窗口把同一场直播再次拆开。

补充测试 `server/test/session-dedupe.test.js`（6 项）：同场次第二段不再新建归档、重启形态下分段仍归属同一场、`deleted` 属主不阻塞新归档、显式分段被识别为自动重连对、不同直播绝不合并、共用 `liveId` 的剪辑片段不被误判为场次属主。

已知未覆盖：修复只阻止**新增**重复。已经落成两个 `done` 文件的重复归档，`status: "merged"` 项会被列表过滤、不会显示，但两个 `done` 需要人工删除多余的那条（工具里「删除」按钮会同时删服务器文件）。

## [1.31.1] - 2026-10-26

### 修复：保留策略会把已归档的正片当作缓存删除（数据丢失事故）

为 1.31.0 回收磁盘时，我手动删除了 5 个 `.official-replays/<liveId>/verified.mp4`，判断依据是「目录里还有 `complete.json`，溯源信息保住了」。**这个判断是错的**：对 `archiveOrigin=official_replay` 的记录，`verified.mp4` 同时是记录的 `filePath`（正片本身）和 `replayRecovery.replayFilePath`。删掉它等于删掉正片，5 条记录随即被标记 `deleted`。

进一步排查发现这不是一次性的手工失误，而是**代码缺陷**——自动保留任务也会做同样的事：

- `sweep()` 把 `replayRecovery.replayFilePath` 列为可回收候选。对官方回放归档，该路径就是主文件。
- `purge()`（水位清理）完全没有主文件保护。它依赖 `storage.inventory()` 的 `kind` 分类，而记录一旦不再处于 `done`，同一个 `verified.mp4` 就会被归为 `residual`/`untracked`，于是被 `unlink`。
- `reclaimNow()` 同样只信任 `kind !== "main"`。

事故中线上日志可见 `water-level purge removed 3 fragment/cache files (5677983456 bytes)`，而它删的正是刚恢复的 3 场正片——恢复后数分钟内再次丢失。

**修复**：新增 `mainFileGuard(records)`，由记录所有权（而非文件名或分类）判定不可删除——任何在非 `deleted`/`merged` 记录中作为 `filePath` 出现的路径一律不可回收。三条删除路径全部接入，并叠加两道冗余：`sweep()` 的候选按 `verified.mp4` 名过滤且再核 `rec.filePath`；`.official-replays` 目录清理时，若目录内任一文件是某记录的主文件则整目录跳过。

**验证**：新增 `server/test/retention-main-file-guard.test.js` 4 项（sweep 不删官方回放正片、sweep 仍能回收真实片段、purge 不删正片、reclaimNow 拒绝被误分类的主文件）。为确认测试不是假通过，把 `purge()` 的保护代码在副本中移除后重跑，`reclaimNow` 用例如预期失败，证明测试确实覆盖该路径。与 `retention.test.js`、`retention-quota.test.js` 合计 13 项通过。

**数据恢复**：5 场全部从官方回放重新下载并经全量 SHA-256 校验，恢复后逐条核对文件存在：杨晔 1.69G、禹佳蔚 1.68G、刘小涵 1.65G、陈琳 2.05G、熊紫轶 2.39G。上线保护后 30 分钟内 retention 删除次数为 0。

## [1.31.0] - 2026-10-26

### 变更：磁盘策略从「固定 10 GiB 门槛」改为「够录完这一场就录」

1.30.1 让空间不足**不再静默**，但门槛本身仍在：只要可用空间低于 10 GiB，一场都不录。在可用空间只有 40 GB 的机器上，这个门槛等于长期拒绝录制——1.30.0 就是这样连续 39 小时一场未录。录制服务的意义是**尽量把直播录下来**，因此门槛改为回答真正的问题：**这场直播能不能录完**。

- **门槛大幅下调**：默认下限由 10 GiB 降为 **2 GiB**（`minFreeGiB` 仍可配置，范围放宽到 0.5 GiB 起）。低于 2 GiB 才拒绝，因为再往下连合并归档的临时空间都不够。
- **按实测码率估算需求**：从历史录像的 `size / 时长` 实测出「每 GiB 小时」，按 3 小时估算本场占用；`requiredBytes = 下限 + 码率 × 3 小时`。短直播门槛低，长演唱会门槛自动提高。实测样本不足时以 0.2 GiB/小时兜底，避免一次误测把门槛压到失真。
- **空间不够先自救**：拒绝之前先调用新增的 `retention.reclaimNow()`，**当场**回收未锁定的片段与缓存（不等 10 分钟的水位轮询）。归档主文件、被 B 站租约锁定、正在分析/切片/排队上传的文件一律不动。
- **估算可覆盖**：`assumedBytesPerHour`（0 = 实测）与 `assumedLiveHours`（默认 3）可在配置中固定，便于已知码率时跳过实测。
- **状态更具体**：`recordingStatus` 增加 `requiredGiB`、`bytesPerHourGiB`、`assumedLiveHours`；`blocked` 增加 `requiredGiB`，页面直接显示「当前可用 X GiB，本次需要 Y GiB」，而不是一个孤零零的下限。
- 页面说明改为「按实测码率 X GiB/小时、估算 3 小时，本次开播约需 Y GiB；空间不足时先自动清理片段与缓存」。

**验证**：`server/test/auto-recorder-space.test.js` 扩到 14 项并全部通过，新增覆盖：3 GiB 小盘经回收后正常开录、低于 2 GiB 下限时拒录并上报、按历史录像实测码率算出需求、显式码率假设覆盖实测、`reclaimNow` 只删未锁定缓存而保留归档主文件。过程中发现并修复两个真实缺陷：`assumedLiveHours` 配置项被硬编码的 `DEFAULT_ASSUMED_HOURS` 遮蔽（配了也不生效）；`reclaimNow` 无法注入 `statfs`/`inventory`，导致无法测试且会读到真实盘。`client/test/auto-record-page.test.js` 9 项通过。

### 修复

- 修复离线转写被自身「录制优先」闸门杀死的问题：`recording()` 此前用存储的状态行推断「有录制在进行」，因此一条残留的 `recording` 记录会让每次转写都被自身守卫终止并循环重试。改为查询录制器实际的活动会话（`pocket48/recorder.listActive()`），存储行降级为兜底并忽略无文件的记录。

- 修复 `media` 子进程错误原因被覆盖的问题：所有 spawn 失败统一报「媒体处理程序无法启动」，ENOENT（ffmpeg/ffprobe 不在 PATH）无法与权限或资源问题区分，误导排查方向。现在保留真实 errno。
- 修复 `lib/cli.js` 的超时选项无效：`child_process.spawn` 不接受 `timeout`（该选项属 `exec`/`execFile`），封面渲染等调用实际没有超时保护，可无限挂起并阻塞整个封面子系统。改为定时器加真实 SIGKILL，默认 60 秒。
- 修复 `routes/config.js` 的配置写入非原子：直接覆写 `config.yaml`，写入期间崩溃或磁盘写满会截断文件，而 `loadConfig()` 吞掉解析错误返回空对象，导致全部设置静默丢失。改为临时文件加 fsync 加 rename，并保留 `.bak` 备份。
- 修复 `routes/config.js` 的 ffmpeg 探测无超时：同样受 `spawn` 不接受 `timeout` 影响，改为手工 5 秒截止。
- 修复公开直播页把后端故障显示为「现在没有正在进行的直播」：请求失败时列表被清空且原因被丢弃，访客会误判为无人开播。现在区分「无法获取」与「确实没有」，失败时保留最近一次已知列表，并在列表可能过期时提示。
- 修正 `AuthGuard` 的放行方向：此前仅在 `authenticated` 显式为 `false` 时拒绝，响应体为空、字段缺失或字段改名都会放行后台。改为要求明确的正向断言（后端成功时返回 `authenticated: true`，否则 401）。
- 修复管理端会话过期后卡死：`adminApi` 没有 401 处理，会话失效后页面继续轮询、每 10 秒弹出一个错误提示且永不跳转登录。现在遇到 401 会跳回登录页并带上返回地址，并防止重复跳转。
