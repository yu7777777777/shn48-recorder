## 发布内容

本版为**纯修复版**，不含新功能，未改变任何接口契约、配置格式或数据格式，故按 PATCH 升版。

### 1. B1 离线转写被自身「录制优先」闸门杀死

- **问题**：`analysis/offline.js` 用一个每 2 秒轮询的 `setInterval` 检查 `recording()`，命中即 `SIGKILL` 已在运行的转写引擎。而 `recording()` 判定的是「存储中存在任意 `status === 'recording'` 的记录」，不是「本次任务自身的媒体正在录制」。
- **后果**：自动录制是常态，任何转写任务在录制期间启动（或运行中恰有直播开始）都会被自身逻辑终止；上层把 `WAIT_RECORDING` 当作可重试错误 `continue`，形成反复重启子进程的循环。残留的 `recording` 状态行会让转写持续失败。
- **修复**：删除运行期轮询，闸门只在任务启动前判定一次；`recording()` 改为查询录制器实际的活动会话（`pocket48/recorder.listActive()`），持久化状态行降级为兜底，且忽略无文件的记录。

### 2. H5 封面渲染子进程无超时

- **问题**：`lib/cli.js` 的 `spawn(bin, args, { timeout })` —— `timeout` 是 `exec`/`execFile` 的选项，`spawn` 不识别，封面渲染等调用实际没有时间上限。
- **后果**：渲染进程可无限挂起并占用并发槽位（后续封面请求持续收到 409），封面子系统整体死锁。
- **修复**：改为挂载真实定时器并在到期时 `SIGKILL` 进程（进程组优先），默认 60 秒（`DEFAULT_TIMEOUT_MS`）；常驻子进程可显式传 `timeoutMs: 0` 关闭。

### 3. H6 配置写入非原子 + ffmpeg 探测无超时

- **问题**：`routes/config.js` 直接覆写 `config.yaml`；写入期间进程被 kill 或磁盘写满会截断文件，而 `loadConfig()` 吞掉解析错误并返回 `{}`，于是全部设置静默丢失、界面显示为默认值。同文件 `/test-ffmpeg` 探测也用了对 `spawn` 无效的 `timeout` 选项。
- **修复**：改为「临时文件 + `fsyncSync` + `renameSync`」原子替换，写前保留 `config.yaml.bak`；探测改为手工 5 秒截止并强制结束。

### 4. H2 公开直播页把后端故障显示为「没有直播」

- **问题**：`pages/PublicLive.jsx` 请求失败时 `setLives([])` 并丢弃原因（`listError` 声明后未被渲染），后端故障与「确实无人开播」渲染成同一个空状态。
- **修复**：区分「无法获取」与「确实为空」，失败时保留最近一次已知列表并在其上方以 `role="status"` 提示可能过期，空列表时给出明确错误文案与自动重试说明。`App.css` 增加 `.public-alert` 的 flex/gap 规则，使前置图标与文字并排。

### 5. H3 `AuthGuard` 放行方向错误（fail-open）

- **问题**：`components/AuthGuard.jsx` 仅在 `session?.authenticated === false` 时拒绝；响应体为空、字段缺失或服务端改名都会放行，且依赖数组为空从不复验。
- **修复**：改为 fail-closed，要求明确的正向断言 `authenticated === true`（`/auth/session` 成功时返回该字段，否则 401），其余一律按未登录跳转登录页。

### 6. H4 管理端会话过期后卡死

- **问题**：`lib/api.js` 没有 401 处理，会话失效后管理页面继续轮询、反复弹出错误提示且永不跳转登录。
- **修复**：`adminApi` 增加响应拦截器，遇 401 跳转 `/admin/login` 并携带 `redirect` 参数；以模块级标志防止重复跳转，并放行登录页自身的会话探测（该探测对未登录访客本就应该 401）。

### 7. CSS 变量未定义导致声明静默失效

- **问题**：`--surface`、`--surface-hover`、`--text-secondary` 被 `ReplayAudit.css`、`App.css`、`AnalysisPanel.css`、`Pocket48.css` 引用，但从未在 `index.css` 定义，也没有回退值，浏览器直接丢弃这些声明。
- **修复**：在 `index.css` 中以别名形式补全定义（`--surface: var(--bg-surface)`、`--surface-hover: var(--bg-card-hover)`、`--text-secondary: var(--text-muted)`），保留既有令牌体系不变。

### 9. H1 落地页首屏体积（代码修复完成，尚未发布）

- **问题**：`components/VideoPlayer.jsx` 在模块顶层 `import Hls from "hls.js"` 与 `import flvjs from "flv.js"`，而该组件被 5 个页面静态引用（`PublicLive`、`PublicReplay`、`Live`、`Video`、`RecordingDetail`）。公开落地页 `/` 只是**列表页**，却因此下载了全部播放器代码。
- **实测**（用容器内 chromium + playwright 记录真实请求，非静态推断）：落地页首屏 **1036.2 KB**，其中 `hls` 579.2 KB + `flv` 152.5 KB = **731.8 KB，占 71%**。
- **修复**：把两个库改为**按需动态 import**（模块级 promise 缓存，避免重复挂载重复拉取）。`mp4` 分支不需要第三方库，保持完全同步；`flv`/`hls` 分支在 `await` 库之后**重新检查 `disposed`**，否则 effect 在分片下载途中被清理会让播放器挂到已分离的 DOM 节点上。
- **实测结果**：首屏 **1036.2 KB → 303.5 KB，减少 732.7 KB（−71%）**。首屏不再请求 `hls`/`flv`；两者仍保留在产物中，播放时才加载。

#### 这次修复中最值得记录的一点：vite 的 CJS 互操作会自行解包，多加 `.default` 反而会坏

把库改成动态 import 时踩到一个**静默失败**：`import("flv.js")` 的结果**不能再取 `.default`**。

产物证据（`VideoPlayer` chunk）：

```
hls -> import("./hls-CUW5jnXJ.js")                  // 未预解包，库在 default 上
flv -> import("./flv-CyUJ4hhH.js").then(e=>e.f)     // vite 已注入解包
```

原因：`hls.js` 是 ES 模块，命名空间上有 `default`；`flv.js` 是 CommonJS，vite 在**构建期**识别其为 CJS 并自动注入 `.then(e => e.f)`，直接返回库对象。因此：

- 若给 flv 也写 `.then(m => m.default)`，vite 的自动解包被顶掉，得到 `undefined`，FLV 播放报 `Cannot read properties of undefined` —— 且**首屏 HTML 照常 200，没有任何报错**，属静默失败。
- 正确写法是**每个库各按其包形态处理**，而不是写一个运行时「猜形状」的通用解包函数。本次先写了这类通用函数（扫描命名空间找 `isSupported`），后经产物分析确认它是多余的、且可能扫到无关对象，已改为逐库显式写法。

**教训**：动态 import 一个 CJS 依赖时，解包方式由打包器在构建期决定，**必须看产物，不能在运行时用裸 `import()` 反推**——运行时的 `import()` 不经过 vite 转换，不会注入 `.then`，据此会得出错误结论。新增 `client/test/player-interop.test.js` 钉住这两种形态（含「给 flv 加 `.default` 会坏」的负向断言）。

## 发布过程中发现并修掉的一个问题

首次构建把版本按 `const { version: APP_VERSION } = require("../lib/version")` 解构，这绑定的是**函数本身**而非调用结果；`JSON.stringify` 会丢弃函数值，于是线上健康接口的 `version` 字段**静默消失**（接口仍返回 200，只是没有版本号）。已在 `server/routes/public.js` 与 `server/index.js` 改为显式调用 `.version()`，并重建镜像。`scripts/verify-image.sh`、`scripts/diag-version-import.sh`、`scripts/diag-health*.sh` 保留为本次排查的可复现证据（对解构写法的正则负向断言已写入构建校验脚本）。

## 镜像构建

- 候选镜像：`shn48-shn48:1.17.6`，大小 **2.32GB**。
- **构建基底为正在运行的 `shn48-shn48:1.17.5`**：本机无 Node，无本地可用的完整构建环境；服务器无法拉取任何镜像（Docker Hub 不可达），也没有裸 node。因此沿用 1.17.5 已验证的「复用基底 + 覆盖源码与产物」路径，即把所有 `node_modules` 排除在构建上下文之外。
- **为什么基底不是 `shn48-asr-runtime:1.2.1`**：该镜像**缺少 cv2**，而 `Dockerfile` 中封面渲染依赖的自检（`/opt/asr-venv/bin/python -c "import cv2; from PIL import Image"`）正是为防止此类基底被静默发布而设计，会直接失败。`scripts/find-cv2-base.sh` 逐个镜像探测后确认：能提供 cv2 4.11.0 与完整 ASR 运行时基础的是 1.17.5 运行镜像本身。
- 构建上下文（`releases/1.17.6/reuse-context`，由 `scripts/build-image.sh` 组装）：`server/`（暂存源码，排除 `node_modules`）、`client/dist/`（本版前端产物）、`VERSION`、取自生产的 `entrypoint.sh`，以及脚本生成的 `Dockerfile.reuse`。
- 需要区分：**运行时依赖层复用自 1.17.5 镜像，但镜像内运行的前端 `client/dist` 是本次 1.17.6 构建产物**（`Dockerfile.reuse` 先 `rm -rf /app/client/dist` 再 `COPY`）；`docker-compose.yml` 不挂载 `client/`，前端只来自镜像。
- **本机维护目录 `1.0.2/client/dist/` 的版本漂移已闭环**：该目录此前时间戳为 **2026-10-11**（1.17.5 发布日），其 `index.html` 与 `PublicLive`/`PublicReplay` chunk 内的版本字符串仍为 `1.17.5` —— 即维护目录里放的是一份**旧的 1.17.5 产物**。这是一个真实陷阱：凡从维护目录构建或比对的人，都会在自认为发布 1.17.6 时实际上发出 1.17.5 的前端。处理方式：确认服务器上已验证的 1.17.6 产物（`index.html` 的 SHA-256 为 `f982d718f16592473abb439642d48acbf93796da8b5f692ee6c0f54865e722bd`，零处 `1.17.5` 引用）后，将其取回并**替换**掉维护目录中的旧产物（旧产物已删除；1.17.5 完整包仍存于 `releases/1.17.5/`，无需在维护目录重复保留）。
- 因此：**当前 `1.0.2/client/dist/` 与入镜像的 1.17.6 产物逐字节一致**，`SHA256SUMS` / `RUNTIME-SHA256SUMS` 已据此重新生成并全量校验通过（297 + 139 项，0 处不符）。

## 过程复盘：为什么八项修复花了两个多小时

结论先给：**八项修复的代码改动本身约 20 分钟；其余时间大致三等分 —— 环境固有复杂度约三分之一，我的返工约三分之一，发布收尾与记录约三分之一。**共产生 43 个脚本（其中约 20 个是一次性诊断脚本），这个数字本身就是问题的一部分。

### 一、环境固有复杂度（约 30–40 分钟，换谁做都省不掉）

- 服务器**无法拉取任何镜像**（Docker Hub 不可达），宿主机**没有裸 `node`/`npm`**。构建路径只能靠 `docker history shn48-shn48:1.17.5` 反推上一版是怎么发出来的，才定位到 `Dockerfile.reuse` 这条「复用基底 + 覆盖源码与产物」的路。
- `shn48-asr-runtime:1.2.1` **缺 `cv2`**，首次构建被封面渲染自检直接挡下。需要逐个镜像探测（`find-cv2-base.sh`）才确认：能提供 cv2 4.11.0 的是**正在运行的 1.17.5 镜像本身**。
- 前端必须在服务器构建（本机按要求不装 Node），装 98 个 devDependencies + `vite build` 本身就要数分钟。
- 宿主机的 compose 是 **v1（`/usr/bin/docker-compose`）**，没有 v2 插件，首次部署因此失败一次并触发自动回滚。
- 本机 shell 环境对远程操作不友好：heredoc 不可用、`python -c` 引号会被吞、`$(...)` 被 PowerShell 解析、`grep` 中的 `\$` 会被转义污染。最终固化出「本地写 `.sh` → `put.py` 上传 → `sed -i 's/\r$//' && bash`」这一模式，但**摸索这个模式本身花了过多时间**。

### 二、我的返工（约 40 分钟，可避免）

1. **误判测试失败，先用五个脚本怀疑代码，最后才发现是测试挂载方式错了**。首次跑 `atomic recording persistence failure...` 失败时，我把 staged 文件叠加在**镜像的旧源码层**上，等于用镜像里 13 个过时文件中的旧 `manager.js`/`store.js` 去跑新测试。正确做法是**以生产源码为基线**（`run-tests-realistic.sh`），改用后该失败立刻消失。`compare-atomic.sh` / `compare-tree.sh` / `compare-image-prod.sh` / `diagnose-atomic.sh` / `diagnose-atomic2.sh` 五个脚本属于这次弯路。**教训：看到失败先核对基线，再怀疑代码。**
2. **`offline.test.js` 因我把 `recording()` 写成无条件 `live.listActive().length>0` 而回归**，改回「活动会话 OR 持久化状态行」才恢复。
3. **最该批评的一项：版本号解构错误本该第一次就写对。** `const { version: APP_VERSION } = require(...)` 绑定的是函数而非调用结果，`JSON.stringify` 丢弃函数值，导致健康接口 200 但**丢失 `version` 字段**。这一个基础错误让「构建 → 验证 → 改 → 重建」整个链路走了两遍，直接多耗 15–20 分钟。代码是我写的，我本应知道 `version` 是函数。
4. 收尾阶段又补了 8 个脚本，其中 `verify-manifests.mjs` 写错两次（PowerShell 转义、`.mjs` 里误用 `require`），`run-client-tests-server.sh` 还因 PowerShell `-NoNewline` 重写导致编码损坏、不得不换名重建。

### 三、可复用的改进项（SOP）

1. **失败先核对基线**（同一镜像内分别跑生产源码与改动源码对比），再怀疑代码 —— 可省掉本次那 5 个诊断脚本。
2. **先在本机用 Adobe 随附的 `node.exe` 做语法与纯逻辑校验**（`esbuild` 解析 JSX、`node --test` 跑不依赖浏览器的用例）。本次收尾时才这样做，5 秒就查出问题；早做可省数轮服务器往返。
3. **远程命令一律写成脚本文件**，不在命令行内嵌引号、`$()` 或 heredoc。
4. **长任务用 `setsid nohup ... > log 2>&1 &` 分离运行**，再轮询日志。本次 `npm install` 因占用单个 SSH 通道而超时，就是没这么做的代价。
5. 记录类脚本应集中一次写好，避免收尾阶段零散追加。
