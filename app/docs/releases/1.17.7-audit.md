## 发布内容

### H1 公开落地页首屏体积

**问题**：`client/src/components/VideoPlayer.jsx` 在模块顶层静态引入两个播放器库：

```js
import Hls from "hls.js";      // 约 579.2 KB
import flvjs from "flv.js";    // 约 152.5 KB
```

而该组件被 5 个页面静态引用：`PublicLive`、`PublicReplay`、`Live`、`Video`、`RecordingDetail`。这抵消了路由分包的意图——**公开落地页 `/` 只是一张直播列表，却下载了全部播放器代码**。

**实测（修复前）**：容器内 `/usr/bin/chromium` + playwright 记录真实网络请求，首屏 **1036.2 KB**，其中 hls 579.2 KB + flv 152.5 KB = **731.8 KB，占 71%**。

**修复**：两个库改为按需动态引入，模块级 promise 缓存以免重复挂载重复拉取。

- `type === "mp4"` 分支不需要第三方库，保持**完全同步**，不引入额外等待。
- `type === "flv"` / `"hls"` 移入 `startFlv()` / `startHls()`，`await` 库之后**重新检查 `disposed`**：否则 effect 可能在分片下载途中被清理，播放器随后挂到已分离的 DOM 节点上。
- 统一以 `start().catch(...)` 兜底，失败时给出可重试提示而非白屏。

**实测（修复后）**：首屏 **1036.2 KB → 303.5 KB，减少 732.7 KB（−71%）**。首屏不再请求 `hls`/`flv`；两者仍保留在产物中（`hls-CUW5jnXJ.js` 580.3 KB、`flv-CyUJ4hhH.js` 152.9 KB），播放时才加载。

## 实施中最重要的一点：vite 的 CJS 互操作会自行解包，多加 `.default` 反而会坏

改成动态 import 时踩到一个**静默失败**，值得单独记录。

产物证据（`VideoPlayer` chunk 内实际生成的代码）：

```
hls -> import("./hls-CUW5jnXJ.js")                    // 未预解包，库在 default 上
flv -> import("./flv-CyUJ4hhH.js").then(e=>e.f)       // vite 已注入解包
```

原因：`hls.js` 是 ES 模块，命名空间上有 `default`；`flv.js` 是 CommonJS，**vite 在构建期**识别其为 CJS，自动注入 `.then(e => e.f)` 并直接返回库对象。

后果：若给 flv 也写 `.then(m => m.default)`，vite 的自动解包被顶掉，得到 `undefined`，FLV 播放报 `Cannot read properties of undefined` —— 而**首页照常 200、控制台不报错、接口正常**，属静默失败，只在实际播放 FLV 流时暴露。

**最终写法按包形态分别处理，而不是写一个运行时"猜形状"的通用解包函数：**

```js
import("hls.js").then(module => module.default)   // 需取 default
import("flv.js")                                  // 直接用，不可再取 default
```

本次一度写了扫描命名空间找 `isSupported` 的通用函数，经产物分析确认它**多余且可能扫到无关对象**，已删除。

**方法论教训**：动态 import 一个 CJS 依赖时，解包方式由打包器在**构建期**决定，**必须看产物**。在运行时用裸 `import()` 反推会得出错误结论——运行时的 `import()` 不经过 vite 转换，不会注入 `.then`，据此会误判 flv 解包失败。

新增 `client/test/player-interop.test.js` 钉住两种形态，含**「给 flv 加 `.default` 会坏」的负向断言**。

## 附带修复：vite 的 VERSION 解析顺序（真实缺陷）

打包时构建产物被标成 `1.17.6`，而所有输入都是 `1.17.7`。产物证据：

```
./VERSION   -> 1.17.7     ← 正确
../VERSION  -> 1.17.6     ← 旧代码优先命中这个
package.json -> 1.17.7
```

`vite.config.js` 的 `resolveVersion()` 原以 `["../VERSION", "./VERSION"]` 顺序探测，**优先信任上层文件**。当源码根就是 client 目录（发布包解包后的常见形态）时，`../VERSION` 指向**包外**，可能读到一个无关的残留文件，于是静默注入错误版本——构建成功、页面正常，只有角标显示一个稍旧的版本号。

这正是 `__APP_VERSION__` 机制本要防住的漂移，却在解析器自身实现里复现了。

**修复**：调整为 `["./VERSION", "../VERSION"]`——**优先读更近、更具体的那份**。

**新增 `client/test/version-resolution.test.js`（6 项）**钉住该顺序，含两条关键断言：

- 解析顺序必须是 `./VERSION` 在前（顺序被调换即回归）；
- 相邻 `1.17.7` + 上层 `1.17.6` 时，结果必须是 `1.17.7`（复现本次事故的确切场景）。



维护目录 `1.0.2/client/dist/` 内是 **1.17.5** 的产物（时间戳 2026-10-11），而从该目录构建或比对会实际发出旧前端。已替换为与线上一致的 1.17.6 产物（`dist/index.html` SHA-256 `f982d718…`），本版再替换为 1.17.7 产物。

## 附带纠正的两个发布流程缺陷

两项都不是本次要修的功能问题，但都会让发布流程的校验失效，属本次发布中暴露并修掉的真问题。

### 1. `client/dist` 版本漂移

维护目录 `1.0.2/client/dist/` 内曾是 **1.17.5** 的产物（时间戳 2026-10-11），而已发布 1.17.6。从该目录构建或比对会实际发出旧前端。已在打包前替换为与镜像一致的产物。

### 2. 运行时清单从本地树生成，描述的不是镜像（本次最严重）

**现象**：首次部署后核对清单，**136 项中 28 项失败**——全部前端文件报 `MISSING`、3 个 `server/_probe*.cjs` 报 `MISSING`，另有若干 `MISMATCH`。而**部署本身完全健康**（容器 healthy、健康接口返回 1.17.7、公网正常）。

**根因**：`RUNTIME-SHA256SUMS` 是在**本机**跑 `manifest.mjs` 生成的，它扫描的是本地工作树：

- 本地 `client/dist/` 是**另一版构建**，chunk 名与镜像完全不同（清单记 `hls-Byw5SIgA.js`，镜像是 `hls-CUW5jnXJ.js`）。**28 项前端"失败"里没有一项是真问题。**
- 更糟的是清单里**混入了 `server/_probe6/7/8.cjs`** ——这三个是我调试时留在 `server/` 的临时脚本，被当成发布内容记录进了清单。

一份描述"没人发布的树"的清单，比没有清单更危险：它会让发布流程习惯性无视自己的校验门。本次如果只看"部署成功"就收工，这个缺陷会一直存在，且下次仍会误导。

**修复**：

- 删除 3 个孤立调试脚本（已确认无人引用）。
- 新增 `scripts/make-runtime-manifest-from-image.sh`：**运行时清单从镜像内生成**，描述的就是将要发布的东西；并加断言，若清单含 `_probe`/`.bak`/`.tmp` 等调试文件则**直接失败**。范围排除 `server/node_modules`（约 1150 个依赖文件，非本版创作内容，会把真正变化的约 140 个文件淹掉）。
- 新增 `scripts/verify-runtime-manifest.mjs`：部署**前**校验清单描述的 chunk 与 `dist` 实际一致。已用"坏的"清单验证过它确实会拦下（报 23 项缺失、播放器 chunk 仅 1/5 命中）。

**修复后**：139 项运行时哈希，**0 缺失、0 不符**，与线上镜像完全一致。

**教训**：发布清单必须**从将要发布的产物**生成，不能从开发工作树生成。二者在正常迭代中必然不同，而这种不同平时表现为一堆噪音告警，恰好掩盖真实的清单错误。

## 诚实边界

- 首屏数据是**线上站点**真实浏览器请求级实测；但测量环境为容器内 chromium，与真实用户网络条件（带宽、缓存、CDN）不同，绝对值会有差异，**比例变化是可靠的**。
- 本版验证覆盖"库能被正确加载"，**未覆盖真实直播流的播放**。
- `client/dist` 与 `RUNTIME-SHA256SUMS` 现已一致，但 `SHA256SUMS`（源码清单，308 项）覆盖的是本地工作树，与镜像内的 `server/` 仍有差异——因为本版是纯前端发布，镜像的 `server/` 沿用 1.17.6 树。这是**预期行为**，不是缺陷；运行时清单才是镜像的权威描述。
