| 项 | 内容 |

| 现象 | 公开直播列表停在加载动画，永远不结束；访客判定页面卡死并关闭 |

## 修复一：公开直播列表永远转圈（本次报障主因）

### 根因

`PublicLive` 的 `loading` 初值为 `true`，而**唯一**能清除它的路径是 `loadLives(false)`：

```js
const [loading, setLoading] = useState(true);
const loadLives = useCallback(async (quiet = false) => {
  if (!quiet) setLoading(true);
  ...
  if (!quiet) setLoading(false);   // 只有非静默路径会清除 loading
}, []);
```

但全页唯一的数据加载入口是轮询，且轮询**始终以静默方式**调用：

```js
usePolling(() => loadLives(true), 30000);   // quiet = true，跳过 setLoading(false)
```

首次挂载走的就是这个轮询回调，因此 `loading` 永远不会被置回 `false`。**即便接口已返回 200 且响应体是空列表，页面也始终停在 spinner 上**。

这是一个典型的"两个各自正确的分支，组合起来错误"的缺陷：静默分支不碰加载态（对轮询而言正确），而首帧也走了静默分支（错误）。

### 修复

挂载时先执行一次**非静默**加载，随后再交给 30 秒轮询做静默刷新：

```js
// The first load must be non-quiet: `loadLives(false)` is the only path that
// clears the initial `loading` flag, and usePolling always polls quietly. ...
useEffect(() => {
  void loadLives();
}, [loadLives]);

usePolling(() => loadLives(true), 30000);
```

> 轮询本身不负责首帧状态，这一点已在代码注释中写明，避免后续又把这行调用删掉。

### 上线后实测（转引自 CHANGELOG，本轮未复测）

- 无直播时页面正确显示「现在没有正在进行的直播」；
- **2.8 秒**内正常结束加载态。

## 修复二：加载状态在请求变慢时被误认为「卡死」

### 问题

直播列表的「正在发现直播…」只有一个**无限旋转的 spinner**：既没有已等待时长，也没有任何可操作项。口袋48 接口偶尔需要十几秒才返回，访客看到循环动画会直接判定页面卡住并关掉页面 —— 而页面其实一直每 30 秒在正常重试。

### 修复

`components/LoadingState.jsx` 新增四个**可选**属性：`slowText` / `slowAfterMs` / `slowHint` / `onRetry`。

- **默认行为完全不变**：不传 `slowText` 时仍是原来的纯 spinner（`slowText = ""` 且 `if (!slowText) return undefined;`，计时器根本不启动）。
- 传入 `slowText` 后从挂载起计时，超过 `slowAfterMs` 就换成说明文案并显示**已等待秒数**，同时按需渲染提示与「重新加载」按钮。
- 计时用 `setInterval` 累加真实耗时（`Date.now()` 差值），不依赖取消后重挂；组件卸载时 `clearInterval`，页面加载完成后不会留下空转的 interval。
- `role="status"` 与 `aria-live="polite"` 保留，慢状态文案变化对读屏可见。

### 接入点

| 页面 | 位置 | 阈值 | 重试入口 |
| --- | --- | --- | --- |
| 公开直播页 | 列表 | 5 秒 | 「重新加载」 |
| 公开直播页 | 播放地址 | 8 秒 | 「重新获取」 |
| 公开重播页 | 列表 | 6 秒 | 「重新加载」 |
| 公开重播页 | 播放地址 | 8 秒 | 「重新获取」 |
| 公开直播页 | 播放器准备阶段 | 8 秒 | **无按钮**（避免与 `VideoPlayer` 自身的重试入口重复） |

`App.css` 新增 `.state-card-slow`、`.state-card-elapsed`（已等待秒数胶囊）、`.state-card-slow-actions`、`.state-card-hint` 样式。

### 实测（转引自 CHANGELOG，本轮未复测）

- 无直播时 **2.8 秒**结束加载态并显示空状态；
- 将 `/api/public/live` 延迟后，**第 6 秒**切换为「比平时慢一些… 已等待 6 秒」并显示提示与「重新加载」；
- 秒数持续递增（**6 → 11 秒**）。

### 阈值设计说明

慢状态阈值按**「用户开始怀疑卡死」**而非接口超时设定（5–8 秒）。接口超时仍是 axios 的 15 秒与后端 `POCKET48_TIMEOUT_MS` 的 12 秒。

**慢提示出现后请求并未中断**，仍在等原始响应；重试按钮只影响下一次轮询 / 重新拉取。

## 回滚

**回滚路径是「镜像 + compose 备份」，不是旧容器。**

```bash
# 1) 恢复 compose 备份
/opt/shn48/docker-compose.yml.pre-1.17.8  ->  /opt/shn48/docker-compose.yml
# 2) 把 image: 改回 shn48-shn48:1.17.7
# 3) 重新起容器
docker compose up -d
```

- 可用镜像：`shn48-shn48:1.17.7`（仍在，已验证可正常启动：`/app/VERSION` 为 1.17.7、`/app/server/index.js` 存在）。
- **重要**：原先设想的「改名保留旧容器」在本机 compose 下**不成立** —— 该主机只有 docker-compose **v1（1.25.0）**，`up -d` 会按 `container_name: shn48-recorder` 重建容器，并把此前的 `shn48-recorder-rollback-1.17.7-*` 一并删除。因此改名的回滚容器**不能**作为回滚依据。
  - 此点与 1.17.7 条目中「compose `up -d` 复用了原容器名，本次没有 per-release 的 1.17.6 旧容器」的记载一致，属同一原因。

## 构建环境偏差（已核验，记录备查）

线上内核为 `5.10.0-15-amd64`，其 overlayfs 层数上限已被 1.17.x 历次 `COPY` 式发布累积到 **169 层**。任何在 1.17.7 镜像之上再改文件系统的 `docker build` 步骤都会报 `max depth exceeded`（`LABEL` / `COPY` / `RUN` 均失败，仅 `FROM` 可通过）。

因此本版改为以 `docker export` 压平后的单层基线（`shn48-shn48:squash-1177`）作为构建基底。压平前后已逐项比对 `/app/VERSION`、`/app/server/index.js`、`/app/client/dist/index.html` 及 asr 解释器哈希一致，并确认 chromium、ffmpeg、tini、entrypoint、`server/node_modules` 均存在。

> 该基线为构建中间物，**不改变运行时内容**。

**运维提示**：overlayfs 层数问题会在后续每次 `COPY` 式发布时复现。建议后续发布统一走上文压平基线的做法，或规划一次基于完整 `Dockerfile` 的重建以归零层数。
